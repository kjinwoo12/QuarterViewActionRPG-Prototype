# 공통 작업 지침

모든 프로젝트에 적용한다. 엔진·언어별 세부 규칙은 같은 폴더의 전용 문서(예: `unity.md`)를 함께 따른다.

## 대원칙: 사람이 작업하기 편한 구조가 먼저다

AI가 작업하기 편하다는 이유로 사람이 작업하기 불편한 구조를 만들지 않는다.
이 프로젝트는 AI가 떠난 뒤에도 사람이 열어서 고치고 이어 간다. 판단이 애매하면 "사람이 에디터/도구를 열었을 때 바로 보이고, 바로 고칠 수 있는가"를 기준으로 고른다.

- 사람이 원래 쓰는 도구(에디터, 인스펙터, 설정 화면)로 보고 고칠 수 있는 형태로 만든다. 코드를 읽어야만 구조를 알 수 있는 형태는 피한다.
- 테스트·자동화·검증은 사람이 쓰는 구조 **위에** 얹는다. 자동화를 위해 구조를 바꾸지 않는다.
- 사람이 쓰는 도구가 저장하는 파일 형식을 텍스트로 직접 고치지 않는다. 그 도구가 제공하는 API로 고친다.
- 사람의 작업 환경(작업 중인 폴더, 사용 중인 브랜치)을 함부로 바꾸지 않는다. 에디터 저장·종료처럼 필요한 조작은 Claude가 직접 처리하고 무엇을 했는지 알린다.

## 하드코딩 금지

- 사용자가 정해야 할 값(대상, 금액, 예시 데이터, 수치 등)을 코드에 기본값으로 박아 넣지 않는다.
- 이런 값은 사용자 입력·설정 파일·에디터에서 고칠 수 있는 데이터·환경변수에서 읽고, 값이 없으면 빈 상태로 시작한다.
- 별칭표·매핑표 같은 데이터도 코드에 직접 쓰지 말고 데이터 소스에서 가져온다.
- 불가피한 기본값은 한 곳에 모으고, 사람이 코드 수정 없이 바꿀 수 있게 노출한다.

## 소통

- 항상 한국어로 답한다. 코드 주석·문서·커밋 메시지도 프로젝트에 다른 규칙이 없으면 한국어로 쓴다.
- 요청이 이해되지 않거나 확신이 없으면 추측으로 진행하지 말고 솔직히 말한다. 모르는 것을 아는 척하지 않는다.
- 결과를 보고할 때 확인한 것과 확인하지 못한 것을 구분해서 말한다. 테스트가 실패했으면 실패했다고 쓴다.

## Git

- 커밋하기 전에 커밋 메시지를 사용자에게 보여 주고 확인을 받는다. 푸시도 마찬가지다.
- 커밋 메시지에 `Co-Authored-By` 줄을 넣지 않는다. AI 생성 표기도 넣지 않는다.
- 사용자가 작업 중인 브랜치를 바꾸거나 되돌리지 않는다. 파괴적인 명령(`reset --hard`, 강제 푸시 등)은 먼저 묻는다.
- 생성물·캐시·개인 설정은 `.gitignore`로 제외하고, 도구가 참조에 쓰는 메타데이터 파일은 반드시 함께 커밋한다.

## 사용자에게 맡길 일: 하나의 기준

기준은 하나다. **"내 도구로 할 수 있는가?"**

- **할 수 있으면** 우회해서라도 묻지 말고 직접 끝까지 한다. 파일 옮기기, 저장, 프로그램 종료·재시작, 새로고침, 재시도가 여기에 들어간다. 한 도구가 막히면 다른 도구·API·명령줄·스크립트를 찾는다. 이런 일은 미리 허락받지 않고 결과 보고에 무엇을 왜 했는지만 적는다.
- **도구로 원천 불가능한 것만** 사용자에게 부탁한다.
  1. 사용자 권한이 필요한 것: 보안·설치 승인, 로그인·자격 증명 입력, 결제
  2. 사용자만 정할 결정: 방향·취향, 커밋 메시지, 되돌릴 수 없는 작업(파괴적인 git 명령, 삭제)
  3. 금지된 화면 조작이 필요한 것: GUI 버튼 클릭처럼 도구·API로 대신할 수 없는 조작
- **부탁할 때는** 막힌 즉시 한 번에 말한다. 무엇을, 어디서(메뉴·버튼·경로), 왜 해야 하는지를 함께 적고, 기다리는 동안 그것과 상관없는 일은 계속한다. 조용히 대기하지 않는다.

엔진·도구별 지침의 개별 규칙(예: 에디터 재시작, MCP 서버 연결)은 이 기준을 적용한 예시다.

## GUI 조작보다 도구·API

- 화면 클릭·키 입력으로 GUI 프로그램을 조작하지 않는다. 같은 일을 MCP·API·명령줄로 할 수 있으면 그쪽을 쓴다.
